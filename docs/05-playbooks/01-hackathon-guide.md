# 黑客松参赛指南（小白版）

> 黑客松（Hackathon）= 限时创客马拉松。它是大学生进入 Web3 **性价比最高的一条路**：逼你学技术、攒作品、认识队友和导师、拿奖金、被投资人 / 招聘方看到。

## 一、为什么一定要参加

- 几周内的成长 > 一学期的泛泛学习（deadline 是最好的老师）；
- 产出一个能写进简历 / 文书的真实项目；
- 免费接触顶级导师（Monad 黑客松可直接向 a16z、Coinbase 等 VC 提问）；
- 获奖 = 奖金 + 曝光 + 实习 / 融资机会；即使不获奖，过程也全是收获。

## 二、去哪里找比赛

| 平台 | 说明 |
|---|---|
| **Devfolio** | 全球（尤其印度 / 加密）黑客松聚合，报名提交一站完成 |
| **Dorahacks** | 中文友好，大量 Web3 / 公联赛事，有 BUIDL 提交 |
| **ETH Global** | 以太坊最知名系列赛，线上线下都有 |
| **Devpost** | 综合黑客松聚合（含很多企业 / 赞助商赛） |
| 各公链官网 / 官方 X | Monad、Solana、Sui 等官方赛（奖金丰厚） |
| 学校 / 城市社群 | 校园黑客松、城市路演日 |

> 行动：现在就注册 Devfolio、Dorahacks 账号，订阅邮件，把「未来 3 个月的比赛」列成一张表。

## 三、赛前准备

### 技能最低配置（第一次参赛前）

- 会用 Git / GitHub 提交代码；
- 能读懂 / 改写简单代码（哪怕主要靠 AI 写，你要能看懂和调试）；
- 对应赛道的基础（智能合约赛：学过 Solidity、部署过测试网合约；AI 赛：会调 API / SDK）；
- **不会的部分靠队友补、靠 AI 学，不必等「全会」再报名**。

### 选题（决定成败的一半）

1. 先看主办方的**赛道和推荐 Idea、Bounty**，优先选「主办方想要、且你做得动」的方向；
2. 好选题三标准：
   - **小而具体**：6 周能做出能跑的 Demo，别一上来做「下一个以太坊」；
   - **有真实用户**：想清楚「谁会用、为什么现在需要」，最好先访谈几个潜在用户；
   - **用到主办方特性**：例如 Monad 赛要用上其高性能 / 低 Gas / 身份等特性，而不是「放哪条链都行」；
3. 用一句话讲清你的项目：「我们帮 \_\_\_（谁）解决 \_\_\_（什么痛点），通过 \_\_\_（什么做法）。」

## 四、组队

### 理想角色配置（3-5 人）

- **技术（合约 / 后端）**：核心逻辑；
- **前端 / 全栈**：把产品做出来、能演示；
- **产品 / 设计**：流程、界面、用户调研；
- **运营 / 文案 / 演示**：写材料、拍 Demo、上台讲（**这是语言 / 文科同学最能发挥的位置**）。

### 去哪里找队友

- 比赛官方 Discord 的 #find-team 频道；
- 学校技术 / 区块链社团；
- 你参加过的活动社群、Wiki 的读者；
- 第一次没队也可「单飞」或被别人捡走，主动在频道介绍自己的技能和想法。

## 五、6 周时间安排（参考 Monad 线上赛）

| 时间 | 重点 |
|---|---|
| 第 1 周 | 定题、组队、用户调研、搭好开发环境和代码仓库 |
| 第 2 周 | 跑通最小闭环（最核心功能先 work，哪怕很丑） |
| 第 3-4 周 | 完善功能、对接 API / 合约、开始做前端 |
| 第 5 周 | 测试、修 bug、准备 Demo 视频和介绍材料 |
| 第 6 周 | 录制 Demo、写项目描述、**持续在官网 Update 更新进展**、提交 |

> 黄金原则：**「Make it work, make it right, make it fast」**——先让它跑起来，再做好、做快。最忌讳追求完美却连 Demo 都没有。

## 六、要提交什么（别漏）

- [ ] **代码仓库**（GitHub，含清晰 README：项目是什么、怎么跑、谁做了什么）；
- [ ] **能跑的产品 / 合约**（核心逻辑必须真的上线 / 部署到测试网，**不接受纯 PPT**）；
- [ ] **Demo 视频**（2-5 分钟，真实操作产品，配讲解）；
- [ ] **项目介绍 / Deck**（痛点、方案、特色、进展、团队）；
- [ ] **过程更新（Update）**：记录每周做了什么、和哪些用户交流——评委明确看这个；
- [ ] 想拿 **Bounty** 记得在官网手动添加，并满足赞助商的特定要求。

## 七、Demo Day：怎么讲（Pitch 结构）

用 3 分钟讲清楚：

1. **痛点**（30 秒）：谁、遇到什么具体问题，现状多糟糕；
2. **方案**（45 秒）：你的产品怎么解决，现场演示最核心的一步；
3. **亮点 / 创新**（45 秒）：为什么你做得成、和现有方案的区别、用了什么新技术；
4. **进展 / 验证**（30 秒）：已经做出什么、有没有用户 / 数据 / 测试结果；
5. **团队 / 下一步**（30 秒）：你们是谁、接下来要做什么、需要什么支持。

> 多展示、少空谈；**能现场跑给评委看，就不要只放截图**。提前演练、计时、准备英文版本。

## 八、评委怎么打分（对照准备）

Monad 的 5 个评分维度（其他比赛大同小异）：

1. **团队与市场就绪度**：有没有真实用户 / 社区 / 反馈（权重高）；
2. **技术实现**：核心逻辑真的跑起来、用了主办方特性；
3. **设计与工艺**：用户是否无需学习就能用；
4. **进展与下一步**：比赛期间的实际更新量；
5. **原创性与洞察**：不是改名换链，对赛道问题有自己的判断。

## 九、大一第一次参赛的特别建议

- 目标先定为「**完整提交一个能跑的小东西**」，获奖是惊喜、不是目标；
- 主动承担你现在就做得好的部分：用户调研、文档、Demo 视频、文案、演示、项目管理；
- 技术上跟队友 / AI 边做边学，哪怕只写了一小段也要 commit；
- 这届来不及（如截止临近）就**先报名、参加活动、加 Discord、看别人怎么做**，下一届正式上；
- 赛后必做：写一篇复盘（做了什么、学到什么、下次改进），发 Wiki。

## 十、常见坑

1. 选题太大，最后啥也没做出来；
2. 只写 PPT / 只做视频，产品跑不起来（直接出局）；
3. 不读规则，错过提交 / Bounty / Update 要求；
4. 队友临时跑路——尽早分工、定期同步、留 buffer；
5. 只顾写代码，忽视用户、文档和演示；
6. 技术没用主办方特性，沦为「放哪都行」的平庸项目。

## 赛后清单

- [ ] 整理代码和文档，把项目放到个人 GitHub 主页置顶；
- [ ] 写复盘、发 X / Wiki；
- [ ] 给帮助过的导师 / 队友致谢、维护关系；
- [ ] 项目有潜力就继续做，报名下一场 / 申请孵化、找实习。
